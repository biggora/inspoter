## Что уже есть: направление «LLM снаружи»

В проекте **уже реализована одна половина** LLM-интеграции — [`src/lib/mcp/`](src/lib/mcp/server.ts) и `POST /api/mcp`: внешний ассистент (Claude Code/Desktop, Cursor) получает доступ к почте, оповещениям, закладкам, контактам, сообщениям, kanban, серверам, сервисам и логам через 109 инструментов со скоупами на уровне API-токена ([`scopes.ts`](src/lib/mcp/scopes.ts)). Тот же набор операций опубликован обычным REST на `/api/v1/**`.

Это важно для дальнейших рассуждений по двум причинам:

1. Сценарий «оператор спрашивает ассистента про свою инфраструктуру» **уже закрыт** — дублировать его чатом внутри дашборда смысла мало.
2. [`defineTool`](src/lib/mcp/tool.ts) уже даёт готовый слой «zod-схема → вызов сервиса → JSON». Любой внутренний агент может переиспользовать ровно эти же определения — стоимость такой интеграции близка к нулю.

Незакрытая половина — **LLM внутри продукта**: то, что работает без человека в цикле (фоновая классификация, дайджесты) и то, что должно жить прямо в UI.

## Рамка: ограничения, которые нельзя ломать

Из архитектуры и PRD вытекают четыре жёстких условия для любой LLM-фичи:

| Ограничение | Источник | Следствие |
| --- | --- | --- |
| Единственный исходящий вызов приложения — Open-Meteo для виджета погоды | [architecture.md §7E.4](docs/architecture.md) | Обращение к внешней модели — архитектурно значимое решение. Нужен явный opt-in и поддержка локальной модели (Ollama/vLLM) как первоклассного режима, а не как «запасного» |
| Секреты провайдеров — AES-256-GCM в БД, per-workspace, не в env | `ProviderCredential`, [`src/lib/crypto`](src/lib/crypto) | Ключ LLM-провайдера обязан переиспользовать ровно этот механизм и `/settings/providers`, а не новую env-переменную |
| Всё поведение описано исполнимыми AC и покрыто e2e; провайдеры имеют детерминированный MOCK-режим | [prd.md](docs/prd.md), [`src/lib/providers`](src/lib/providers/registry.ts) | Без MOCK-режима LLM-слой сделает Playwright-набор недетерминированным. Это блокирующее требование, а не «хорошо бы» |
| Модульный монолит без очередей, Redis и внешних воркеров | [architecture.md §1](docs/architecture.md) | Асинхронные LLM-задачи должны идти по уже существующему паттерну `MailFilterActionJob` + in-process scheduler |

Пятый принцип я бы добавил сам, исходя из культуры проекта: **LLM предлагает, детерминированный код исполняет**. Результат работы модели должен материализоваться в обычную сущность (правило, метка, категория, черновик), которую оператор видит, правит и откатывает — а не в скрытое решение внутри рантайма.

## Минимальный каркас — РЕАЛИЗОВАН (2026-08-02)

```
src/lib/llm/
  contract.ts    LlmProvider: complete() / embed(), типизированные ошибки (category: auth/rate_limit/timeout/upstream/invalid_response)
  registry.ts    выбор провайдера по учётным данным workspace (нет credential → null, слой выключен)
  mock.ts        детерминированные ответы для unit + e2e (FNV-1a fingerprint, без сети)
  openai.ts      OpenAI-совместимый HTTP: покрывает Ollama, vLLM, LM Studio, OpenRouter, OpenAI
```

Реализовано по образцу [`src/lib/providers`](../src/lib/providers/registry.ts) — тот же контракт «MOCK/REAL», та же редакция секретов в логах (§7.6 архитектуры). `openai.ts` намеренно не переиспользует `providers/http.ts`: тот ретраит трижды, что не подходит для вызова модели (повтор стоит токенов, а таймаут обычно значит «модель ещё генерирует») — одна попытка на вызов.

Учётные данные: `ProviderType.OPENAI_COMPATIBLE` (миграция `20260802120000_llm_provider`) поверх существующего `ProviderCredential` (baseUrl, model, apiKey, mode внутри зашифрованного payload) — настройка появилась на `/settings/providers` тем же путём, что у остальных провайдеров, под маскированием и без изменений в бэкапе.

Три вещи, заложенные вместе с каркасом:
- **Аудит**: [`src/lib/services/llm.ts`](../src/lib/services/llm.ts) — единственная точка входа; каждый дошедший до модели вызов пишет `Activity` (`llm_complete`/`llm_embed`) с моделью, режимом драйвера и числом токенов.
- **Лимит**: `LLM_CALL_RATE_LIMIT`/`LLM_CALL_RATE_WINDOW_MS` (по умолчанию 60/час на workspace) — по образцу `MAIL_SEND_RATE_LIMIT`.
- **Kill switch**: без `OPENAI_COMPATIBLE`-credential `registry.ts` возвращает `null`, `llm.ts` отвечает `unsupported` — слой выключен полностью, как сейчас ведут себя разделы без провайдера.

Что каркас **не** решает сам — это задача каждой будущей фичи из каталога сценариев ниже: он не выбирает модель, не формирует промпт и не решает, что показать оператору.

## Где LLM применять не стоит

Валидация входных данных (zod остаётся единственным источником истины), авторизация и скоупы, power-действия над серверами, мутации DNS без подтверждения, автоматическая отправка почты, разбор метрик агента, порог `stale`, численные прогнозы. Всё это — детерминированная логика с исполнимыми AC; замена её моделью ухудшит и точность, и тестируемость.

Решённый вопрос: **исходящий трафик к внешней облачной модели допустим по умолчанию**, наравне с локальной — ограничивающего флага в каркасе нет. Рекомендуемый режим (README, «Модели ИИ (LLM)») — локальная модель, но выбор остаётся за оператором через `baseUrl` учётных данных. Это значит, что тела писем/логов/оповещений в промпт может попасть, если оператор сам подключит облачного провайдера — эту цену явно называет README при подключении.
